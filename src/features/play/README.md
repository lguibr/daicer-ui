# Player lifecycle

`operations.graphql` consumes the authoritative backend `game-contract.ts` SDL. Generate with `yarn graphql-codegen --config codegen.game.ts`; this reads the sibling backend's actual standalone schema without a running server. Never edit `generated.ts` manually. Legacy generated output is preserved for inactive and debug callers.

The exact generated output file is exempt from source lint; its types and operations remain checked by TypeScript and offline codegen. The codegen configuration itself is included in the ESLint TypeScript project.

`useRoomView` owns one serial poll loop per room and authenticated viewer. It uses no shared Apollo result cache, aborts/discards old requests, rejects other rooms and older revisions, and refreshes on reconnect. Access denial clears the projection; transport failures retain only the current viewer's last successful projection with an explicit reconnecting/error state. An empty response is never a successful room.

`useRoomMutation` scopes pending state and retry IDs to the authenticated user and room. Its operation key must include the operation name and full input (except request ID). Uncertain failures retain their ID for retries, including page reload through session storage where available. Definitive failed operation results and `OPERATION_FAILED` retire their ID: the backend's `src/api/game/services/turn-lifecycle.ts` claim policy requires a fresh ID after a terminal failure. Other GraphQL errors do not imply safe replay with a fresh ID. Old-context completions cannot update the new context or retire another context's IDs. Callers retain input on failure and only navigate/clear drafts after a non-undefined successful result.

The SDL is a declarative contract, not proof that runtime resolvers are installed. RoomView exposes typed persisted terrain cells filtered by the same field of view as entities. Gameplay uses these cells directly, with no preview terrain substitution. Cross-project acceptance requires separate runtime integration evidence.

Active routes use `PlayerRoomsPage`, `PlayerCharacterPage`, and `PlayerRoomPage`. The latter mounts a viewer-and-room-keyed `PlayerSession`, the sole room poller. Lobby readiness, start, intent/pass and owner resolution use server capabilities. Access failures unmount all projected messages and positions. Pending requests retain drafts; transport reconnects disable actions until refreshed. The map draws authorized terrain and entity placeholders. A click on a visible walkable cell fills an editable movement intent. Only the explicit Submit action sends it to the existing proposal pipeline. Suggestions belong to the current room, viewer and turn, and cannot overwrite submitted or reconnecting drafts.

`proposing` means private intent is saved while its command is prepared. The backend can project an expired proposal as `needs_revision` after 120 seconds with the same room revision, so equal-revision views must still refresh. A mutation receipt bridges the wait for its matching projection and prevents duplicate submission; once matched, the projection owns status again. Revision requests retain the draft. Intent text is bounded to the backend's 4000-character limit.

Creation submits supported world configuration and language; the old DM configuration route redirects to world configuration. Existing DM/custom-character/game screens remain preserved but inactive. Debug creation retains `?target=debug` and uses canonical room IDs. The `/room/:roomId` alias only redirects; preexisting links containing join codes still require joining through the landing page, because a read route does not implicitly join rooms. Back to rooms is navigation, not a membership mutation. No leave or socket-presence capability is invented.

Terrain includes world identity, content revision, authoritative chunk size and z bounds. Sparse client chunks retain negative coordinates and omit unknown cells. A null terrain projection disables backend capabilities and displays an unavailable map; client code never generates replacement terrain.
